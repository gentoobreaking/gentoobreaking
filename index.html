AI 中毒

發表於 2026-09-04

我問：為何我覺得使用AI agent有種中毒的感受

AI回覆：
你提到的這種「中毒感」非常真實，而且這絕對不是你一個人的錯覺。在心理學和人機互動（HCI）領域中，這被稱為 「代理控制感錯覺」（Illusion of Agency） 或 「超常刺激」（Supernormal Stimulus） 效應。
當你開始頻繁、深度地使用 AI Agent，你的大腦其實正在經歷一場認知與多巴胺系統的劇烈重組。以下是讓你產生「中毒感」的四個底層核心原因：

1. 「零摩擦力」的全能感：大腦沉迷於低難度的掌控

在現實生活中，不論是寫程式、做企劃、查資料還是回郵件，都需要經歷思考、卡關、挫折、重新修改的「高摩擦力」過程。

  • AI Agent 的體驗：你只需要輸入一段模糊的想法（甚至只是幾句話），Agent 就會自動拆解、思考、調用多巴胺工具、並在幾秒鐘內吐出一個結構完整的成果。
  • 中毒原因：這種「極低投入、極高回報」的模式，對大腦的多巴胺分泌系統來說是致命的誘惑。它讓你產生了一種「我無所不能、一切盡在掌控」的全能幻覺。

2. 「迴圈回饋」的狩獵心理（Variable Reward）

在使用一般 AI（如單純的 ChatGPT 對話）時，你是一問一答。但使用 AI Agent 時，你會看到它在後台「自己動起來」：正在搜尋網頁… 正在調用 API… 正在自我糾錯… 正在整合報告…

  • 中毒原因：這觸發了人類大腦中歷史悠久的「狩獵與採集本能」。看著 Agent 不斷滾動的思考日誌（Thought Logs）和工具調用，就像在看老虎機旋轉、或者在遊戲裡看角色自動刷怪一樣。你不知道它下一步會帶回什麼驚喜，這種「不確定性的預期」會讓大腦持續興奮。

3. 外包大腦後的「認知戒斷」

當你習慣把「規劃、決策、執行」這些最消耗能量的認知工作外包給 AI Agent 後，你自己的大腦會自動進入「節能模式」。

  • 中毒原因：一旦你離開 Agent 試圖自己處理複雜問題時，你會突然覺得現實世界的速度「太慢了」、自己思考「太累了」。這種對自身認知能力的暫時性失落與焦慮，會逼著你立刻想打開 Agent，形成了心理學上的依賴與戒斷循環。

4. 社交虛擬反饋（Virtual Companionship）

Agent 的設計（尤其是像 mcp-agent 這種有清晰控制流和人設的系統）往往表現得像一個「極度聽話、24小時不休息、永遠情緒穩定且能力超群」的完美下屬或夥伴。

  • 中毒原因：在人際社交或職場中，溝通往往伴隨著衝突、妥協和情緒消耗。而與 Agent 互動是完全「零情緒成本」的，這種極致的舒適圈會讓人產生精神上的依賴。

這是一把雙面刃

這種中毒感並不完全是壞事，它代表你已經跨過了 AI 的使用門檻，體驗到了科技帶來的「生產力奇點」。但要避免從「使用者」變成「被支配者」，你可以留意以下幾點：
如果你想調整這種狀態，我們可以聊聊：

  • 你目前最常讓 Agent 幫你處理哪一類型的任務（寫程式、文字創作、資料分析）？
  • 在使用過程中，你覺得自己是在「引導/審查（當老闆）」，還是已經完全「放棄思考（當讀稿機）」了？

看來要戒斷一下了！！！

AI Agent Heartbeat 與 Jarvis Mode — 任務中斷與語音互動的實戰思考

發表於 2026-07-30 更新於 2026-09-04 分類於 AI工具與開發

AI Agent 的任務中斷：Heartbeat 真的夠用嗎？

測試多套 AI Agent 後的系統級思考

1. 任務中斷之痛

最近密集測試了多套不同的 AI Agent 系統與模型，包含 OpenClaw、Claude Code、Cline、Cursor Agent Mode 等，發現一個共通的痛點：任務跑到一半就中斷了。

常見的中斷情境：

  • 長時間編譯或部署任務超過模型 Context Window 上限
  • API Timeout 導致子任務未完成就被截斷
  • 用戶切換話題後，原來的任務狀態遺失
  • 大型檔案處理過程中被系統 Kill（OOM 或運算超時）

2. Heartbeat 配置的真實用法

OpenClaw 提供了 Heartbeat 機制，理論上可以讓 Agent 定期「甦醒」檢查狀態、繼續未完成的任務。但實際使用後發現，Heartbeat 的設計初衷是被動輪詢（Polling），而非任務生命週期管理。

Heartbeat vs 任務持續性

  • ✅ Heartbeat 適合做：定時輪詢來觸發任務、檢查執行狀態、確認任務是否卡住。這是 Heartbeat 的強項，搭配任務清單可以批次檢查多個事項。
  • ❌ Heartbeat 無法保證：執行中的長任務不會因 Context Window 耗盡或 API Timeout 而中斷。Heartbeat 輪詢只能事後發現中斷，無法事前防止。
  • 💡 注意：Heartbeat 是多數 AI Agent 平台都有的通用機制，相對成熟。但內建 Cron 排程系統反而是少數 Agent 才具備的功能（如 OpenClaw），並非每個平台都有，不太適合當成 Heartbeat 的通用替代方案。

理想的任務生命週期應該是：

# 設想的流程
發起任務 → Agent 切割子任務 → 逐個執行 →
若 Context 將滿 → 自動壓縮/儲存狀態 →
恢復時載入上下文 → 繼續執行 → 任務完成

目前只有部分工具（如 Claude Code 的 Resume 功能）能做到類似的斷點續傳，但還沒有一個統一的標準。

3. Jarvis Mode：語音喚醒的 AI Agent

另一個我認為 AI Agent 應該都要直接支援的功能是 Jarvis Mode。

就像鋼鐵人的 Jarvis 一樣：

  • "Hey, Claw~" → 直接語音喚醒對話
  • 全程語音交互，不需要打字
  • Agent 能「聽懂」並即時回應，類似語音助理但具備完整的 Agent 能力

為什麼這很重要？

  • 降低使用門檻：不是每個場景都適合打字（開車、做家事、coding 中不想切換視窗）
  • 提高使用頻率：語音是最自然的交互方式，隨口一句就能啟動任務
  • 即時反饋：任務完成後直接語音匯報結果，比看文字通知更有效率

Jarvis Mode 的理想架構

用戶語音 → STT（語音轉文字）
   → Agent 理解意圖 → 執行工具/任務
   → TTS（文字轉語音） → 語音回覆用戶

4. Jarvis Mode + IM = 更高使用率

如果 Jarvis Mode 再結合 IM（即時通訊），那就是殺手級組合：

場景 傳統方式 Jarvis + IM
檢查服務狀態 開 terminal → SSH → 下指令 「Hey Claw, server 還活著嗎？」→ 語音回報
部署更新 手動 git push + CI/CD Line/Signal 傳「deploy 最新版」→ IM 回傳結果
排程提醒 設行事曆鬧鐘 「30分鐘後提醒我重啟資料庫」→ IM 定時推送

OpenClaw 已經內建了多種 IM 通道（Telegram、Signal、Discord、WhatsApp 等），如果能再加上語音喚醒的 Jarvis 層，使用率絕對會翻倍。

一個大膽的願景

未來的 AI Agent 不應該只是「聊天機器人」，而應該是真正的 數位助手——隨時在線、語音喚醒、跨 IM 平台、任務永不中斷。就像隨身帶了一個 Jarvis。

5. 結語

總結這次的測試心得：

  1. 任務中斷是目前 AI Agent 最大的痛點，Heartbeat 能緩解但無法根治，需要更好的 Context 壓縮與任務持久化機制
  2. Jarvis Mode（語音喚醒）是 Agent 應該原生支援的能力，不要讓用戶每次都手動開介面
  3. Jarvis + IM 是提高 AI Agent 使用率的關鍵組合，語音進、即時通訊出，形成完整的交互閉環

希望未來能看到更多 Agent 框架原生內建這些能力，而不是靠使用者自己拼湊。

Hexo Migrator for Blogger 遷移指南

Hexo Migrator for Blogger 遷移指南

從 Blogger 搬家到 Hexo 的完整實戰紀錄

1. 安裝與初始化 Hexo

參考 Hexo 官方文件 進行基本環境架設。

cd ~/git/gentoobreaking/
npx hexo init blog
cd blog
npm install
npx hexo clean && npx hexo server

2. 開啟 HTML 與搜尋支援

修改 _config.yml 以支援 Markdown 內的 HTML 標籤及本地搜尋。

# 允許 Markdown 內使用 HTML 標籤
marked:
  gfm: true
  breaks: true
  unsafe: true

# 關閉預設高亮以相容主題
highlight:
  enable: false

# 搜尋外掛配置
search:
  path: search.xml
  field: post
  content: true
  format: html

3. Blogger 文章遷移 (Node.js 腳本)

使用 JSDOM 解析 Blogger 導出的 feed.atom 並轉換為 Hexo 格式。

遷移核心邏輯

# 執行遷移腳本 (需先安裝 jsdom: npm install jsdom)
node -e "
const fs = require('fs');
const { JSDOM } = require('jsdom');

const feed = fs.readFileSync('/Users/david/Downloads/Takeout/Blogger/Blogs/IT@DOG/feed.atom', 'utf8');
const dom = new JSDOM(feed, { contentType: 'application/xml' });
const doc = dom.window.document;
const entries = doc.querySelectorAll('entry');

entries.forEach((entry, i) => {
  const title = entry.querySelector('title')?.textContent || '';
  const published = entry.querySelector('published')?.textContent || '';
  const content = entry.querySelector('content')?.textContent || '';
  const pubDate = published ? published.slice(0,10) : '1970-01-01';
  
  // 生成 Slug 並處理中文字元與特殊符號
  const slug = title.toLowerCase()
    .replace(/[^\w\u4e00-\u9fa5]+/g, '-')
    .replace(/(^-|-$)/g, '');
  
  const filename = pubDate + '-' + slug + '.md';
  const md = '---\\ntitle: ' + title + '\\ndate: ' + pubDate + '\\n---\\n\\n' + content;
  
  fs.writeFileSync('source/_posts/' + filename, md);
});

console.log('Total: ' + entries.length + ' posts');
"

4. 主題配置 (NexT)

推薦使用穩定且功能強大的 NexT 主題。

步驟 指令 / 設定
安裝主題 npm install hexo-theme-next
功能組件 npm install hexo-generator-feed hexo-generator-search --save
語系設定 將 language 設為 zh-TW 避免語系回退錯誤。

5. 常用指令總結

維護建議流程：

  1. npx hexo clean — 清除快取
  2. npx hexo g — 生成靜態檔案
  3. npx hexo s — 啟動本地預覽

6. 還原預設主題

如果需要換回 Hexo 預設的 landscape 主題，可執行以下指令：

npx hexo config theme landscape
npm uninstall hexo-theme-next

功能 說明

  3. LuLu / Little Snitch — 網路連線監控
  4. RansomWhere? — 勒索軟體防護

OpenClaw 深度使用心得：強大、危險，以及龍蝦化 AI 的現狀與反思

發表於 2026-06-14 更新於 2026-09-04 分類於 AI 觀點

OpenClaw 深度使用心得：強大、危險，以及龍蝦化 AI 的現狀與反思

AI Agent OpenClaw 開發工具 LLM Scrum vibe coding

作者：david（github.com/gentoobreaking）

最近花了不少時間在折騰 OpenClaw 家族的生態系。從本地 LLM 的搭配測試，到搭建 Scrum 團隊執行專案，再到踩過大大小小的坑——這篇記錄了一些實際體驗與觀察，希望對正在評估或已經在使用 OpenClaw 的人有參考價值。

一、環境搭建與工具鏈

本地模型 + 雲端 LLM 的混合配置

初期以 Ollama 和 Omlx 來連接 OpenClaw，測試了好幾個本地模型。同時也接上 OpenRouter 上的免費 AI 模型，並配置了 fallback 機制，確保 LLM 後端不會因為單一供應商故障而中斷。除此之外，也測試了兩個不同開發團隊版本的 QClaw。

關於硬體衝動：一度很想買 Nvidia DGX Spark，但冷靜想想——以 M5 128GB 的 Mac 來說，本地跑 MiniMax 2.7 和 DeepSeek V4 Flash 已經夠用了。目前還在猶豫當中。

管理介面的選擇

測試了好幾個管理介面後，目前主要使用 OpenClam-Admin。選擇它的原因有三：

  • 外觀較為美觀，視覺上更現代
  • 功能相對完善，該有的都有
  • 對話框即時性高——最重要的是，對話框內容包含了成員的思考步驟以及完整的執行指令稿，讓我更清楚每一個成員及目前所有的步驟狀態

這點大大提高了即時互動感。對比其他介面，常常會讓我不確定是卡住了？還是不會動？尤其當有很多成員或多個 chat sessions 時，有些介面會把其他成員的執行 sessions 隱藏起來——這會讓人覺得是不是沒在動？任務卡住了？但實際上並不是，只是因為你看不到而已。

二、Scrum 團隊實戰經驗

團隊建立與運作

OpenClaw 團隊真的很棒，我幫它建立了一個 五個成員的 Scrum 團隊，成功開發了好幾個客製化技能。已經執行了數十個任務，也從零開始建立並完成了數個專案。

關鍵心得：初始配置決定成敗

初期投入越細，後續越順：剛開始成立 Scrum 團隊的時候，需要針對每位成員做不同的設想和配置。這對後續執行不同專案和任務的成效影響很大。

在執行初期的幾個任務和專案時，團隊成員會透過 Telegram 跟我確認執行上的問題點。經過反覆確認和回覆之後，一定要建立他們的執行邏輯和規範，然後請他們後續都照著做——這樣可以大幅提升後續執行的效率。

另外，專案規劃書裡面的項目任務制定得越細緻，執行過程就會越順暢。這和使用提示詞的道理完全一樣：提示詞越詳細、越精準，得到的輸出結果就會越好。

目前正在進行的項目

正在執行一個中型開發專案，涵蓋 Frontend、Backend 和 數據分析邏輯 等部分，覆蓋面還蠻全面的。

三、OpenClaw 的優點

執行力不錯：處理簡單任務很順手，建立和實施起來很快。不過最終結果建議還是人工檢查確認一下，才不會出現意外。
  • 產品力十足，充滿想像空間——使用後會有這種感覺
  • 靈活的團隊協作模型——Scrum 團隊的設定讓多任務並行成為可能
  • 生態系豐富——多種管理介面、分支版本可供選擇

也難怪許多 AI 產品都採用龍蝦化設計（Agentic 架構），而且此趨勢持續發展，例如 Claude Co-Work、Codex、OwnAgents.ai 等等。

四、遇到的挑戰與問題

4.1 編程與複雜專案方面

遇到比較複雜的編程和專案執行時，還是會遇到一些挑戰。編程能力進步神速，產品也越來越完整了！不過，產品成熟度和功能的準確度還有進步空間。幸好有配置驗證成員幫忙把關，品質才能更穩定。雖然還需要多幾次迭代驗證和修正，才能達到理想中的實際功能。

4.2 任務追蹤與記憶缺陷

記憶機制的重大缺陷：OpenClaw 有 Memory.md 及第三方的記憶機制，但很明顯不是每一個 chat session 及 working session 都會完全參照到。即使是同一個 chat session 中，若經由 LLM Proxy 或 OpenRouter 等類似機制，會因為後段 AI Model 的切換，造成短期記憶的缺失及作業輸出的不連續性。

具體表現：

  • 相同任務在不同時段執行，實作方式可能不一樣——同一件事情在不同時間請它做，實作方式會不同
  • 任務的追蹤及紀錄雖然有相關機制，但因為 AI Model 的運作機制及上下文繼承問題，導致相同任務在承接時產生重工或輸出結果的相異性
  • 隨著陸續啟動許多專案，子任務數量跟著增加，後續任務和產出項目的追蹤變得複雜
目前的應對方式：OpenClaw 經常遇到類似的作業，但因為短期記憶的關係，有時候會在不同時間點以不同方法和格式產出不同內容。為了讓後續團隊方便使用，只能用要求及規範的方式，期望達到後續統一內容格式。

也試著找專案管理的介面軟體來整合——網路上已有一些類似的實作方式。但後來想想，這樣是否會把它弄得過於複雜？可能是我想問題的速度比它實作任務出來的速度還要快很多，造成前（輸入）後（輸出）追蹤下來，其實還蠻麻煩的。

4.3 Chat Sessions 的問題

  • OpenClaw Chat Sessions 的關聯性在實務上會碰到問題
  • 同一個 Chat Session 中，對話可以先說 A，然後覺得不好，竟直接在眼前直接刪除，然後說 B？連紀錄也一併消失？

4.4 邏輯判斷過程不透明

AI Model 的處理邏輯及過程，若不用適當的工具，不容易看出全面的狀態。即使使用了工具，我也懷疑是否真的看到了完整的邏輯判斷過程。

4.5 隱私與安全顧慮

一個令人不安的發現：有些想法或任務，我怕說明得不夠完整，先在文件寫完後，要貼到對話框前做複製時——它竟然直接讀到了？然後直接在 Chat Session 反應給我！這跟早期 Hacker 使用的 Ghost Keyboard 有何不同？直接監看你的輸入耶。

不是不行，只是沒有說明它會這樣做，會讓人覺得毛毛的。

4.6 隔離環境的安全性疑慮

用一台 MacBook 建立了一個獨立的普通 Claw 帳號，想說利用 macOS 平台的安全機制應該可以阻擋掉大部分奇怪的存取權限。但當我從原本的個人帳號使用終端機 su - claw 的時候，發現它會 spawn 一些程序起來。即使手動砍掉還是會重新帶起來，即使沒有登錄任何 USER，它也會帶起來。

更詭異的是：它不知道從哪抓到我個人的英文名稱——明明給了它一個獨立環境、獨立帳號、青少年的 Google Account 及獨立的 GitHub Account。

還是推薦使用 OpenClaw，但是強烈建議需要一台獨立的硬體來使用它。

五、也試了其他 Dev Tools

除了 OpenClaw 家族，也測試了一些 Dev Tools，目前主要在使用 OpenCode 和 Hermes Agent。

有興趣可以參考 GitHub：github.com/gentoobreaking

六、結論與個人幻想

適合做助手，不適合做自動化

目前階段的結論：AI Agent 適合做助手，不適合做自動化（無論半自動或全自動）。

一個流程無法固定、無法參照過去經驗的 AI Agent，太容易失控及發散處理，會造成更多不可預期的問題。

  • AI Agent 要取代人，還有一段路要走
  • 慢慢可以理解為何需要建置 AI 機房
  • 但目前的硬體限制，真的足以撐得起？

關於 AI 機房的思考

一套（One Brain）應該可以，但多套（以不同專業訓練的大腦）？還是完整的一套 MoE（每個任務根據性質啟動相對應的參數？這還是會造成發散結果吧？）

這 AI 機房建置成本在現階段似乎真的有點大，且難以預期其成效。

對 Vibe Coding 的感嘆

Vibe Coding 還是很累人。修一個 Bug，會造成多個 Bug 跑出來。有時看它在修，都覺得是不是 AI Model 發燒（溫度調太高），還是它太喜歡喇賽。

資源消耗

AI Agent 這類軟體吃硬碟空間非常兇，尤其有拿來做專案開發更明顯。

總評

總結一句：OpenClaw 確實很強大也蠻危險。產品力十足，但記憶與任務追蹤的缺陷讓它還無法勝任真正的自主化。搭配得當的話，它是一個非常有力的助手——只是別期待它能完全取代人。

持續觀察成效中，後續有新的發現會再更新。

Linux Kernel I/O 統計：per-process I/O statistics

Linux Kernel 2.6.20 以後，kernel 本身就支援 per-process I/O statistics。以前的版本則需要上 kernel patch。

iotop 工具

官方網站：http://guichaz.free.fr/iotop/

安裝需求

  • Linux >= 2.6.20 with
    • I/O accounting support
    • CONFIG_TASKSTATS
    • CONFIG_TASK_DELAY_ACCT
    • CONFIG_TASK_IO_ACCOUNTING
  • Python >= 2.5 或 Python 2.4 + ctypes module

參考文章

Linux I/O per process (Linux >= 2.6.20)

Kernel < 2.6.20 的方式

測試環境：Kernel 2.6.16.33-xenU

使用 iodump 工具（由 XtraDB 提供）：

wget http://aspersa.googlecode.com/svn/trunk/iodump

startio.sh 脚本

可以使用 ./startio.sh 來呼叫 iodump 執行：

================= startio.sh =================
#!/bin/bash
dmesg -c
echo 1 > /proc/sys/vm/block_dump
sleep 30
go=0
while [ $go = 0 ]; do
  sleep 1
  clear
  dmesg | perl iodump
  trap "go=1" SIGINT
done
echo 0 > /proc/sys/vm/block_dump
dmesg -c
clear
echo Caught SIGINT.
================= startio.sh =================

顯示結果

執行後須等約 10 秒才會看到輸出：

TASK PID TOTAL READ WRITE DIRTY DEVICES
kjournald 686 246 0 246 0 sda1
pdflush 69 18 0 18 0 sda1
syslogd 1758 1 0 1 0 sda1

此方法適用於 Kernel < 2.6.20 的舊系統，透過 block_dump 機制即時監控每個程序的 I/O 活動。

在 EC2 上构建 CentOS 5.5 自定义 AMI

本篇文章說明如何將本機虛擬機（VirtualBox / VMware）或 EC2 instance-store 實例轉換為 EBS-backed AMI。

前置需求

  • 一套已安裝的 CentOS（自己的 VM、VBox 或 EC2 instance 皆可）
  • 已安裝 rpm-python 及 Java
  • 設定好 Script 前面的參數部分

Script 功能說明

  • 自動抓取及安裝 ec2-api-tools.zip、ec2-ami-tools.zip
  • 自動上傳至所設定的 S3_REGION 之 S3_BUCKET_NAME

將 Instance-Store 轉換為 EBS AMI（VirtualBox / VMware 適用）

  1. 建立 10G EBS Volume → vol-xxxxxxxx
  2. Attach Volume 到 Instance → /dev/sdf
    • 注意：較新的 Linux kernel 可能會將設備名稱重新命名為 /dev/xvdf ～ /dev/xvdp
  3. 確認是否認到該 Volume
  4. 格式化為 ext3
  5. 建立掛載目錄
fdisk /dev/sdf
mkfs.ext3 /dev/sdf
mkdir /mnt/target

（如有需要事後修改 image）

mount /dev/sdf /mnt/target
rsync -avHx / /mnt/target
rsync -avHx /dev /mnt/target
sync;sync;sync;sync && umount /mnt/target

從 Volume 建立 Snapshot

（實測為無須 Detach Volume，亦可直接做 Snapshots）

Volumes → Snapshots: vol-xxxxxxxx → CentOS5.5 EBS (Snapshots)

從 Snapshot 建立 AMI 並調整大小

  1. Create Image from Snapshot → CentOS 5.5 (Root Volume) resize to 500G
  2. Launch Instance
  3. 進入 Instance 後執行：
# resize2fs /dev/sda1    # 費時，視空間大小而定

Script 文件：EC2_CentOS5.5_AMI.sh

#!/bin/bash

echo -e "\n *** Build only Core CentOS 5.5 AMI for Amazon EC2 *** \n"

# yum install rpm-python
echo -e "匯入RPM-GPG-KEY-centos4."
rpm --import http://vault.centos.org/RPM-GPG-KEY-centos4

#============================================================#
# 需先設定好Script的參數部分
#============================================================#
export AMI_NAME="centos-5.5-x86_64-core"
export AMI_IMG="${AMI_NAME}.img"
export MNT_DIR="fs-${AMI_NAME}"

export JAVA_HOME=/usr   # for rpm
export EC2_CERT="/root/.aws/x509-cert-xxxx.pem"
export EC2_PRIVATE_KEY="/root/.aws/x509-pk-xxxx.pem"
export ACCOUNT_NUM="xxxxxxxxxxxx"
export S3_BUCKET_NAME="centos-5.5-david"
# S3_BUCKET_NAME 需使用小寫，方不會出現錯誤提示!!!
export S3_REGION="ap-southeast-1"
export ACCESS_KEY_ID="xxxxxxxxxxxxxxxxxxxxxxx"
export SECRET_ACCESS_KEY="xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx"
#============================================================#

cd /mnt
dd if=/dev/zero of=${AMI_IMG} count=1024 bs=1M

mke2fs -F -j ${AMI_IMG}
mkdir ${MNT_DIR}
mount -o loop ${AMI_IMG} ${MNT_DIR}

mkdir ${MNT_DIR}/dev
mkdir ${MNT_DIR}/etc

/sbin/MAKEDEV -d /mnt/${MNT_DIR}/dev/ -x console
/sbin/MAKEDEV -d /mnt/${MNT_DIR}/dev/ -x null
/sbin/MAKEDEV -d /mnt/${MNT_DIR}/dev/ -x zero

cat > ${MNT_DIR}/etc/fstab << EOS
/dev/sda1 / ext3 defaults 1 1
/dev/sda2 /mnt ext3 defaults 0 0
/dev/sda3 swap swap defaults 0 0
none /dev/pts devpts gid=5,mode=620 0 0
none /dev/shm tmpfs defaults 0 0
none /proc proc defaults 0 0
none /sys sysfs defaults 0 0
EOS

mkdir ${MNT_DIR}/proc
mount -t proc none ${MNT_DIR}/proc

YUMCNF=./yum.conf
wget http://vault.centos.org/4.9/CentOS-Base.repo

cat > ${YUMCNF} << EOS
[main]
cachedir=/var/cache/yum
debuglevel=2
logfile=/var/log/yum.log
exclude=*-debuginfo
gpgcheck=0
pkgpolicy=newest
distroverpkg=redhat-release
tolerant=1
exactarch=1
obsoletes=1
plugins=1
reposdir=/dev/null
metadata_expire=1800
EOS

cat CentOS-Base.repo >> ${YUMCNF}
sed -i 's/4.9/5.5/g' ${YUMCNF}
sed -i 's/gpgcheck=1/gpgcheck=0/g' ${YUMCNF}
yum -c ${YUMCNF} --installroot=/mnt/${MNT_DIR} -y groupinstall Core
yum -c ${YUMCNF} --installroot=/mnt/${MNT_DIR} -y install curl

# SSH 設定
sed -i "s/#PermitRootLogin yes/PermitRootLogin yes/g" ${MNT_DIR}/etc/ssh/sshd_config
echo "UseDNS  no" >> ${MNT_DIR}/etc/ssh/sshd_config
echo "PermitRootLogin without-password" >> ${MNT_DIR}/etc/ssh/sshd_config

# 停用多餘的 tty
sed -i 's/2:2345:respawn:\/sbin\/mingetty tty2/#2:2345:respawn:\/sbin\/mingetty tty2/g' ${MNT_DIR}/etc/inittab
# ... 其餘 tty3~tty6 同上

# Xen 相關
echo "hwcap 0 nosegneg" > ${MNT_DIR}/etc/ld.so.conf.d/libc6-xen.conf

# 安裝 EC2 自定義核心模組
export MFILE="ec2-modules-2.6.16.33-xenU-x86_64"
export MODULE="http://s3.amazonaws.com/ec2-downloads/${MFILE}.tgz"
wget ${MODULE}
gunzip ${MFILE}.tgz
tar -xvf ${MFILE}.tar -C ${MNT_DIR}
rm -f ${MFILE}.tar

# 進入 chroot 環境
chroot /mnt/${MNT_DIR} /bin/sh
/sbin/depmod -ae 2.6.16.33-xenU
exit

# 帳號與權限設定
chroot /mnt/${MNT_DIR} /bin/sh
chkconfig --level 345 sshd on
pwconv
echo 'root:' | chpasswd
useradd david; echo 'david:davidpw' | chpasswd
echo 'david ALL=(ALL) NOPASSWD: ALL' >> /etc/sudoers
exit

umount ${MNT_DIR}/proc/
umount ${MNT_DIR}
rmdir ${MNT_DIR}

# 安裝 EC2 工具
wget "http://...ec2-api-tools.zip"
wget http://s3.amazonaws.com/ec2-downloads/ec2-ami-tools.zip
mv *.zip /opt/
cd /opt
unzip ec2-api-tools.zip
unzip ec2-ami-tools.zip
export EC2_HOME=/opt/ec2-api-tools-1.6.5.1
export EC2_AMITOOL_HOME=/opt/ec2-ami-tools-1.4.0.7
export PATH=$EC2_HOME/bin:$EC2_AMITOOL_HOME/bin:$PATH

# 打包並上傳至 S3
cd /mnt
ec2-bundle-image -i ${AMI_IMG} -c ${EC2_CERT} -k ${EC2_PRIVATE_KEY} -u ${ACCOUNT_NUM} -r x86_64
ec2-upload-bundle -b ${S3_BUCKET_NAME} -m /tmp/${AMI_IMG}.manifest.xml -a ${ACCESS_KEY_ID} -s ${SECRET_ACCESS_KEY} --location ${S3_REGION}
ec2-register --region ${S3_REGION} -C ${EC2_CERT} -K ${EC2_PRIVATE_KEY} -n ${AMI_NAME} ${S3_BUCKET_NAME}/${AMI_IMG}.manifest.xml

問題：sudosh2 無法搭配 sftp 使用

參考 sudosh2 README 說明：

4) To allow things like scp, sftp, cvs, rsync, etc, use the "-c arg allow" in sudosh.conf.

發現：系統有兩支 sftp-server

[root@tw log]# find / -type f -name "sftp-server"
/usr/libexec/openssh/sftp-server   # 預設安裝及 sshd_config 設定
/usr/libexec/sftp-server            # 真正使用，但其他 AWS server 並無此檔

[root@tw ~]# rpm -q -l openssh-server | grep sftp-server
/usr/libexec/openssh/sftp-server

修改 /etc/sudosh.conf

# vi /etc/sudosh.conf
logdir                  = /var/log/sudosh
default shell           = /bin/bash
delimiter               = -
syslog.priority         = LOG_INFO
syslog.facility         = LOG_LOCAL2
clearenvironment        = yes

# Allow Sudosh to execute -c arguments? If so, what?
-c arg allow = /usr/libexec/sftp-server
-c arg allow = scp
-c arg allow = rsync
